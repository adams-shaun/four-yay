# Client Model Transitions and Motion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build sub-projects 0 and 5 of the table UI rework:

- **A normalized client model boundary** (`ClientView` + `PendingDecision` + `Transition[]`) with the gorge adapter behind it, shaped so a Manabrew snapshot-diff adapter slots in later.
- **A pure snapshot-diff transition deriver** (the Manabrew half of the spec), tested, with no Manabrew network code.
- **Motion:** zone-move flights, damage float + shake, life ticks, pile bumps, an ordered queue with stagger and a cap that collapses big batches, a user speed setting (off / fast / normal), `prefers-reduced-motion` forcing off, and motion that never blocks input.
- **Log:** move transitions add a `from → to` zone chip to transcript rows.

**Architecture:**

- `web/src/lib/clientmodel/types.ts` defines the model: `ClientView` (today an alias of the gorge wire `View`), `PendingDecision` (alias of `Decision`), `ZoneRef`, the `Transition` union and the `ClientModelSource` interface (`view`, `decision`, `onTransitions`).
- `web/src/lib/clientmodel/events.ts` maps explicit gorge events (`move_zone`, `draw`, `stack_push`, `trigger_push`/`ability_push`, `tap`/`untap`, `damage`, `counter`, `player_counter_change`, `token_create`) to transitions, using the views on either side to place seats.
- `web/src/lib/clientmodel/snapshotdiff.ts` is `diffViews(prev, next)`: moved A→B by object id, hidden-zone count moves (draws, casts from a hidden hand), tapped/untapped, damage, counters, life, and stack push/pop.
- `web/src/lib/clientmodel/gorge.ts` picks, for one live forward view step, the events when the DVR holds every seq of the step and the snapshot diff otherwise; life always comes from the diff. `TransitionBus` is the tiny pub/sub.
- `MatchState` (`lib/match.svelte.ts`) **is** the gorge adapter: it implements `ClientModelSource`, and its one view-assignment edge (`setRenderedView`) emits the step's transitions synchronously *before* it assigns the new view, so a listener still sees the old DOM.
- `web/src/lib/motion/plan.ts` turns one batch of transitions into timed `MotionStep`s (pure). `web/src/lib/motion/queue.ts` plays batches in order with an injected clock (pure, testable). `web/src/lib/motion/settings.ts` + `settings.svelte.ts` hold the speed setting.
- `web/src/components/MotionLayer.svelte` is the overlay: it captures source rects/clones when a batch is emitted, measures destinations after `tick()`, and runs Web Animations. `TickNumber.svelte` ticks life totals. `MotionSpeedControl.svelte` is the setting.

**Tech Stack:** Svelte 5 (runes), TypeScript, Vitest (node environment), Web Animations API, Playwright for the smoke.

**Spec:** `docs/superpowers/specs/2026-09-28-client-table-ui-rework-design.md`, sections "0. Client model adapter and transitions" and "5. Motion".

## Rulings

- Ruling: `MatchState` is the gorge adapter rather than a new wrapper class — it already owns the stream→view reduction; wrapping it would move every `Table.svelte` read for no behaviour change and collide with lanes B and C. Components that migrate read it through the `ClientModelSource` interface.
- Ruling: `ClientView` and `PendingDecision` are type aliases of the gorge `View` and `Decision` for now — the gorge view already is the normalized shape the components read; a Manabrew adapter projects `gameView` into it. Renaming every component's props is lanes B/C's migration, not this lane's.
- Ruling: the snapshot-diff deriver runs over `ClientView`, not over Manabrew's raw `gameView` — the future adapter projects first, then diffs, so the deriver is shared and testable today. It is also the gorge adapter's fallback.
- Ruling: for a gorge step the events win when the DVR holds every seq in `(prevSeq, nextSeq]`, otherwise the diff is used — the spectator path receives events before the view, but the seated path backfills its redacted events concurrently with the view fetch, so they are usually not there yet; waiting for them would delay the board. Life always comes from the diff, because damage to a player changes life without a `life` event.
- Ruling: only a live, same-match, forward step emits transitions. A snapshot, rewind, DVR scrub or match change emits a `reset`, which finishes the queue.
- Ruling: consecutive moves of one object in a batch coalesce into one flight from its first source to its last destination — the intermediate zone (usually the stack) is already gone from the DOM when the batch plays.
- Ruling: the cap is 8 flights per batch; past it the moves collapse to one group flight per destination pile, carrying a `×N` badge.
- Ruling: "a decision arriving finishes the queue" is applied when the viewer's own decision seq changes (seated), before that step's batch is enqueued, so the batch that arrives with the decision still plays; any pointerdown or keydown also finishes the queue. Destination cards are faded (never `pointer-events:none`, never removed) while a flight lands, so they stay clickable. A spectator has no input to protect, so only input finishes the queue for them.
- Ruling: the queue keeps at most 2 pending batches; older pending batches are dropped (the DOM already shows their end state).
- Ruling: speed timings — normal: flight 460 ms, stagger 80 ms, float 900 ms, life tick 600 ms; fast: 220 / 35 / 520 / 280 ms; off: nothing. `prefers-reduced-motion: reduce` forces off. Default normal.
- Ruling: the speed control lives in the Play options' Layout section (a view preference, like hand peek) as its own component. Lane B's layout drawer can adopt the component.
- Ruling: the "feed transitions to the log" item is a zone chip (`hand → stack`) on transcript rows whose event is a move, rendered from the same event→transition mapping. A transitions-built log (Manabrew's case) is `transitionLine()` in `clientmodel/log.ts`, tested but not mounted — gorge already has server log lines.
- Ruling: flight anchors — a card flies from/to its `[data-obj]` element when one is on screen; otherwise from/to the zone anchor. The anchor contract is `[data-motion-anchor="<seat>:<zone>"]` (for lane B's new seat boxes), falling back to today's `[data-seat=N] [data-pile=<zone>]`, `[data-player-pill=N]`, `.identity[data-seat=N]`, `[data-seat=N]`, and the rail's stack section for the stack.
- Ruling: shakes animate the CSS `translate` property, which composes with a tapped card's `transform` rotation instead of replacing it.
